# 任务成功锚点与失败重跑方案

> 状态：**方案（未落地）** ｜ 本文档只做设计，不含实现代码。
> 目标读者：后续 craft 模式落地时对照执行。

---

## 一、背景与目标

### 问题
当前引擎里"任务完成"的信号是 **`#done`**，但现有任务 JSON 里大量步骤的 `失败跳转` 都写 `#done`（如 `成长.json:14/23/31`、`主线任务.json:43`、`画册.json:30/39`、`领取邮件.json:14`…）。也就是：

- **识别不到 = 走 `#done` = 引擎判 `Success = true`**

结果就是"**打开界面/点了一下入口就算成功**"，**任务实际没干成也会被判成功**，调度器不会重跑、不会报错。这是本次要解决的核心问题。

### 目标
给任务加一个"**真正干成了**"的正向信号，并据此自动重跑：

1. 任务必须走完**设计好的收尾步骤**才算成功，否则判**未成功**；
2. 未成功时**当场完整重跑**（不等下一轮调度，避免被高优先级任务抢走）；
3. 重跑次数用尽才进冷却，交回正常调度；
4. 超时不算失败（保持原行为）；
5. 子任务（如 `野外挂机` 里跑的 `领取邮件`）不受此机制影响。

## 二、核心概念

### 2.1 成功锚点（`成功锚点`）
任务 JSON 头部新增字段，值为**步骤名数组**：

- **任一命中即算成功**（用户明确："1 任一"）。
- 不写该字段 = 沿用旧行为（走到 `#done` 即成功），**所有存量任务不受影响**。
- 语义：这是"任务真正干成了"的标志步骤。

```json
"成功锚点": ["退出"]
```

### 2.2 失败重跑（`失败重跑`）
任务 JSON 头部新增字段，值为**次数**：

- 跑完一遍**没命中任何锚点** → 判未成功 → 允许重跑的遍数。
- 不写/写 0 = 不重跑（旧行为）。
- 字段名定稿为 **`失败重跑`**（用户："2 失败重试啊。。" → 后修正为"改成 失败重跑呗那就"）。

```json
"失败重跑": 3
```

### 2.3 超时不算失败
用户明确："1超时肯定不算失败的"。任务级 `最大执行秒` 到期仍按原逻辑收工，**不因超时额外判未成功、不触发重跑**。

### 2.4 子任务隔离
- `野外挂机` 的 `挂机中` 插件会同步 `跑子任务`（`plugin/挂机中.go:93`），跑 9 个任务流水线。
- **是否判定锚点，只看该任务自己的 JSON 有没有配 `成功锚点`**（不按"是不是子任务"分）。
  - 子任务目标 JSON（如 `领取邮件.json`）**未配锚点** → 不判；
  - 日后把某子任务改成 `自动调度: true` 并**配了锚点** → 它自己那条引擎自然就会判（用户："1 不是啊 他自动调度打开的时候就重跑要好用"）。
- **必须保留**：打标带任务名（`MarkPluginWork(ctx.TaskName)`），防止外层任务跑子任务时，子任务打标串进外层任务的判定。

## 三、判定机制：对外一套，对内两分支

### 3.1 为什么是"两套来源"
"锚点命中"的信息分布在**两个地方**：

| 锚点类型 | 例子 | 引擎能不能自己判定 |
|---|---|---|
| 普通步骤锚点 | `退出`、`主线进行中`、`关闭`、`挂机中` | **能**：引擎看得见"识别命中 + 执行了动作" |
| 插件步骤锚点 | `福利领取`、`自动买药` | **不能**：插件内部干了什么只有插件知道 |

**对外只暴露一套**（同一个 `成功锚点` 字段、同一个重跑逻辑、同一个判定入口），差异只落在**引擎内部的一个分支判断**上。

### 3.2 两个命中来源

- **普通步骤**：该步骤在 `runNode` 主流程里"识别命中 + `doAction` 执行"即算命中。
  - 参照位置：`task/engine.go:404-405`（`// ── 执行动作 ──` → `e.doAction(step, x, y)`）。
- **插件步骤**：插件**返回 ok** 且 **`plugin.PluginWorked(任务名)` 已被置位**，才算命中。
  - 用户明确："肯定不是 插件步骤ok 就ok的啊"——**插件返回 ok 本身不算成功**。
  - 参照位置：`task/engine.go:315-340`（`if step.Plugin {` 分支）。

### 3.3 插件打标规则（关键决策）
- **不打在"点中某个目标"那行**（用户纠正："也不一定是点到红点啊。有可能 红点都点没了"），而是打在插件的**正常收尾 return 分支**上。
- 每个插件有**两条正常收尾路径，都要打标**（用户："有可能 有2个 一个是 有东西的时候一个是没啥东西的时候"）：
  1. **有东西可干** → 干完 → 正常结束；
  2. **没东西可干**（红点已领完 / 不缺药 / 背包已空）→ 正常空手结束。
- 中途 `return "no"`（卡住 / 识别不到界面 / 超时提前退出）**一律不打标**。

> 举例（福利领取）：扫到红点 → 点完 → `处理完成` → 打标；一个红点都没有 → `外层无红点 → 结束` → **也打标**；扫到一半卡死超时 → 没走到这两句 → **不打标** → 判未成功 → 重跑。

### 3.4 引擎侧判定流程

```
跑完一遍 → 配了「成功锚点」且一次都没命中?
    是 → ExecResult.Success = false，ExecResult.NoAnchor = true（不算 Error、不算超时）
    否 → 按原逻辑（Success / Error / 超时）
```

## 四、重跑机制

### 4.1 为什么放在 executeTask 内部（而不是交给下一轮调度）
最初想法是"判未成功 → 进冷却 → 等下一轮调度再跑"。**但这是错的**：

`PickNext` 按优先级挑任务（`bot/scheduler.go` → `task.Loader.PickNext`），该任务冷却好了也可能**被更高优先级的可运行任务抢走**，甚至**永远轮不到**。那不叫"重跑第二遍"。

用户原话："调度器下一轮完整重跑一遍？下一轮万一跑的不是这个任务咋办" → 因此**重跑必须在 `executeTask` 内部当场再跑**。

### 4.2 重跑循环（落在 `bot/scheduler.go` 的 `executeTask`，`:234`~`:368`）

```
s.running = t                          // 单飞锁
loop:
    新建引擎 + 新建 ctx（独立计时/独立超时）
    清空本任务的插件打标
    跑一遍（现有"超时 select + 等引擎退出"逻辑不变）
    if 超时            → 收工（不算失败、不重跑）
    if 命中锚点/旧行为  → 收工（按原逻辑 Success/Failed）
    if NoAnchor:
        if 重跑次数 < 失败重跑:
            RandomSleep(6000, 10000)    // 间隔 6~10 秒（与任务间隔延时同值）
            goto loop                   // 原地接着跑下一遍
        else:
            判未成功 → 进 JSON 冷却秒 → 收工
```

### 4.3 关键约束
- **单飞锁 `s.running` 全程不释放**（`:236` 置上，`:333` 才清空）→ 重跑期间别的任务插不进来。
- 重跑**不经过 `PickNext`、不看优先级**。
- **每遍独立计时、独立超时**（每遍新建 `context` 与引擎），与"重新跑一遍"语义一致。
- 次数用尽 → 判未成功、按 JSON `冷却秒` 正常进冷却，之后才交回正常调度。
- 间隔固定 **6~10 秒**（用户："RandomSleep(3000,5000) 改成 6-10"）。

### 4.4 任务间隔延时要同步改
- `bot/scheduler.go:337` 现有任务间隔延时 `core.RandomSleep(3000, 5000)` → **改为 `core.RandomSleep(6000, 10000)`**（用户："任务轮转 延时 害得加"）。
- 重跑间隔与任务间隔延时**取同一个值 6~10 秒**，保持一致。
- ⚠️ 注意现有延时在单飞锁**之外**（`:333 s.running = nil` 之后、`:335` 才 Sleep）—— 它管的是"任务彻底结束 → 下一个任务开始"；重跑延时是"这一遍跑完 → 原地跑下一遍"，在锁内（`goto loop` 之前），两者是两处独立延时，都要有。

## 七、边界与约束

1. **单飞锁不释放**：重跑全程 `s.running` 保持，防串台。
2. **子任务不判定**：按"目标 JSON 有没有配锚点"自然区分；带任务名打标防串标。
3. **每遍独立超时**：每遍新建 ctx，`最大执行秒` 各自计时（否则长任务重跑必撞超时，重跑无意义）。
4. **超时不重跑**：超时保持原行为。
5. **锚点表为空 = 旧行为**：不配 `成功锚点` 的任务完全不受影响。
6. **插件 ok ≠ 成功**：必须"返回 ok + 已打标"。
7. **巡检/弹窗命中不计入锚点**：只认主流程 `runNode` 真正执行的步骤。
8. **日志**：重跑相关日志沿用现有 `core.LogWithTimef` 风格；坐标日志用 `x1,y1,x2,y2` 四段逗号分隔。

- 超时：仍按原行为收工，不触发重跑。
