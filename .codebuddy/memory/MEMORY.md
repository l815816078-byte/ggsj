## 硬约束（必须遵守，用户多次纠正）
- **🔴 未经用户允许，一律不准加新东西**（新变量、新常量、新函数、新字段、新判断、新配置项、新日志……一律不许自作主张加）。用户只让"修"就只修，只让"改这一处"就只改这一处。想加先问、等明确答复再动手。这条是最高优先级，压过"我觉得这样更好/更完善"。（2026-10-14 用户原话："在我没允许的情况下不准加新东西"；同类教训还有"别瞎几把改了""你他妈倒是修啊""我只让你学循环，没让你加方案/加方法"）
- **严格遵守 CLAUDE.md，落笔前先读对应小节逐条对照**，不要按"通用编程直觉"写。该项目多处规则是"反通用"的（内联、禁自造方法、嵌套结构不动），原则是 **项目规则 > 我的判断**。
- **一次性/单处使用的坐标、常量、颜色、阈值一律内联写数字**，禁止抽成 `var/const`。只有同一值被 2 处及以上引用才允许抽变量（抽了就得处处复用）。反例：`每日任务区域=[583,163,758,639]` 被用户痛批删除。
- **不新增 md 里没有的方法/变量/封装**。曾自创 `ClickRecogLoop` 被批；"识别到就点它"统一用 `ClickRecog`。
- **循环自己写 `deadline := time.Now().Add(...)` + `for ...Before(deadline)` + `if IsStopped()`**，不编造"最大轮数"常量（除非用户明说）。
- **不要动用户的嵌套循环结构**（`for A { for B {} }` 的层级/顺序/归属一律保持）。
- **修改前先查 CLAUDE.md 与同类已有实现照抄**，不"自己发挥"。
- **只改用户点名的那一项，不顺带改旁边的字段**（2026-10-13 被批）：用户说"给预设加个区域 / 加个字段"，就只加那一项，**已有字段（相似度、坐标偏移、返回中间坐标…）原样保留**，不要"顺手优化/连带调整"。
- **识别日志里的 `sim:1.000` 不等于"用户指定了阈值"**：用户贴 `区域1:(left:..,top:..,sim:1.000)` 这类**识别日志**时，sim 只是日志自带输出。CLAUDE.md:42 那条"1/1.000 → 写 0.95"**只适用于用户明确要求配阈值**的场景；用户只是要加区域/改别的，已有相似度一律不动。

## 架构事实（排查过、已确认）
- 「挂机中」插件的 `跑子任务()` 会在 野外挂机/每日任务 执行期间**同步嵌套**跑 9 个子任务（plugin/挂机中.go:63-95），走 `plugin.RunTask → Scheduler.RunTaskNow → executeTask` 新建引擎。日志里看到"任务 A 执行中冒出任务 B"通常是这个，不是调度器并发。
- `Scheduler.RunTaskNow` 只校验目标任务自身是否 Running，**没有全局单飞锁**。
- `Scheduler.executeTask` 的超时分支只置状态就 return，不终止 `engine.Execute` 的 goroutine → 存在野协程继续点击。
