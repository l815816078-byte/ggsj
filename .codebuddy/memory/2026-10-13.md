## 排查：每日任务 / 野外挂机「串」的根因（只诊断，未改码）
- 现象：日志里 每日任务 与 野外挂机 两个引擎同时打印（`已用12m29s/上限-7m29s` 还在巡检跳转）、野外挂机 挂机中 期间突然出现 每日任务 日志。
- 根因1（引擎超时形同虚设）：`task/engine.go` runNode 的 `if tried && time.Now().After(nodeDl)` 只在"同层重试"时才会被走到；StartUp↔挂机中 这种**跳转即 return/递归**的路由循环每层都把 `tried` 重置为 false，跳转前不查 deadline → `最大执行秒` 永不生效，任务不会自己结束。
- 根因2（野协程）：`bot/scheduler.go` executeTask 的 `case <-ctx.Done()` 只把状态置 TaskFailed 就 return，`engine.Execute` 不接收 ctx，且 `rs.Interrupted` 全程没人置 true（只在 `Reset()` 里清 false）、`plugin.IsStopped()` 只认脚本停止 → 超时后引擎 goroutine 继续点击。
- 根因3（并发=串）：tick() 是同步的，上一轮超时返回后下一轮 tick 立刻 PickNext 挑下一个任务（野外挂机 冷却10s）→ 同一进程两套引擎同时在跑，日志交错；RunTask 子任务走同一条 executeTask，子任务超时同样留野协程。
- 修复方向（待用户确认）：① runNode 进入前加任务级 deadline 硬检查直接返回；② executeTask 超时分支置 `t.RunState().Interrupted = true`（引擎 217 行已有该检查），并在任务开始时置回 false。
- 补充（第二次排查，仍未改码）：**「挂机中」的 `跑子任务()` 是设计内的同步嵌套**，`plugin/挂机中.go:63-95` 在 野外挂机/每日任务 的「挂机中」步骤里 `RunTask()` 依次跑 9 个子任务（领取邮件/领取成就/福利领取/灵力修炼/气运显现/背包物品/画册/加护/成长）。链路 `plugin.RunTask → bot/scheduler.go:150 RunTaskNow → :216 executeTask → 新建 PipelineEngine`。`RunTaskNow:156` 只查目标任务自己是否 Running，**不查"当前有没有别的任务在跑"**，所以嵌套畅通。那 9 个子任务 JSON 全是 `自动调度:false`，只可能从这条路径触发。
- 嵌套的**隔离/补偿**（外层不会真的废掉）：子任务写自己的 RuntimeTask 状态，外层 state 仍 Running；`挂机中.go:89` 把子任务耗时补回 `上次打怪时间`，不会误判"100秒没打怪"；RunState 各自独立；`onTaskComplete/Error` 的 `t.Reset()` 只影响子任务。
- 嵌套的**真伤害**：① HUD 状态名被覆盖且不恢复（`scheduler.go:223` 每个 executeTask 都写 `正在执行: %s`，子任务跑完外层名不回写）；② HUD 超时进度行被清（`:253` 子任务 goroutine 退出时 `SetTaskProgress("",0,0)`）；③ 游戏画面被改成子任务界面，`挂机中.go:92-94` 的 `ClearPopups()` 只清弹窗列表里的（退出/关闭），**不在弹窗列表的面板不会关** → 回到挂机中后识别不到 自动攻击开启中/怪物 → 走失败跳转重开，极端情况 `#done` 收工。
- 伤害**基本是一次性**的：`挂机中.go:71-79` + `scheduler.go:180-183` 子任务跑完压 10000~20000 秒冷却（3~5.5h），后续轮次 `RunTask` 全返回 false（冷却中跳过）。冷却被清（ResetTaskCooldown / 全量重启的 resetAllTasks）后才会每轮都跑 → 用户"以前没发现、现在串"的原因。
- 耗时风险：外层 3000s 是共享的，9 个子任务各 300~1500s，累加远超外层时限。
- **为什么 executeTask 要把 `engine.Execute` 放进 goroutine**（第三次追问，未改码）：不是为了并发执行任务（tick() 全程同步阻塞），而是为了**让主流程能在超时时脱身**。`engine.Execute(rs)` 是纯同步调用且**不接收 ctx**，一调用就阻塞住最长 3000 秒；Go 又**没有从外部强杀 goroutine 的能力**，所以要"超时保护"只能把它扔进子 goroutine，主流程用 `select { <-ctx.Done() | <-doneCh }` 谁先来走谁。代价：超时分支只是"主流程不等了"，子 goroutine 完全不知情继续跑（协作式取消，只能靠它自己查 `plugin.IsStopped()` / `rs.Interrupted` 退出，见 engine.go:82/217）。`doneCh` 缓冲必须是 1，否则超时 return 后没人收，子 goroutine 会永久卡在发送语句上泄漏。
- **由此定下 B 方案含义**：不动计时，只在 `case <-ctx.Done()` 分支里补"置停止信号（`rs.Interrupted=true`）+ 带兜底短超时等 `doneCh`"，保证旧引擎真退出后调度器才继续挑下一个任务。A 方案是改计时（子任务耗时从外层预算里扣），两者不冲突。
