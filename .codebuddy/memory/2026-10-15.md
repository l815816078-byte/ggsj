### 📚 咨询：业界"点按钮进面板再干活"怎么做的（用户："不要看我代码 别人这种东西是怎么做的"）

给用户的通用答案（**未涉及本项目代码**，仅参考）：

1. **页面判定（state detection）+ 导航原子化** 两件事分开。判"我在哪个页面"用该页**独有且不被遮挡的锚点**（标题/独有图标），**不用"会消失的入口按钮"反推**。
2. 三种主流范式：
   - **A 显式等待（explicit wait）**：Selenium `WebDriverWait+ExpectedConditions`、Appium、Airtest `wait()/exists()`、Sikuli `wait(img,10)` —— `click(入口)` 后紧跟 `wait_until(目标页锚点出现)`，**卡在这次调用里等**，不等就干活 = 竞态。

3. 四条共性：锚点唯一且不被遮挡 / 导航 = click + wait（原子）/ 有 deadline + 重试 + 回滚 / 幂等（任意状态进入都收敛）。
4. **与本项目的差别**：业界是**主动确认**"到了没"（wait / state check），本项目是**被动交给主循环下一轮再看** —— 能跑，但把"导航失败"和"时间流逝"混在一起，失败只能靠外层计数兜。

### 💬 用户问「入口那个 return 为什么必须」（仅解释，未改代码）

### 💬 用户问「return 跟其他方法比效率如何」（仅讨论，未改代码）

**核对出的关键数值**：`mian/主流程.go:298` 主循环末尾当前是 **`core.RandomSleep(1000, 1500)`**（不是旧记录里的 300~500）→ **分帧"每步一格"的代价 = 每步约 1.0~1.5 秒**（还要加识别 + 刷HUD + 超时/卡死检测）。

结论要点（供以后解释复用）：
1. **分帧 return 几乎不额外花钱**：它就是**把主循环本来就要睡的那 1~1.5 秒当等待窗口**用（面板渲染正好在这个窗口里完成）。唯一亏的是**等待粒度粗**（只能 1~1.5s 后回来看，不能 300ms 就回来）。

5. `else` 嵌套 / `goto` 与 `return` **运行时完全等价**（Go 无条件跳转），只差可读性；goroutine 异步等对单线程点击流程无意义且引入竞态。

### 💬 追问「每次 return 下轮进来又要重新识别，这个效率」（仅讨论，未改代码）

### 💬 用户问「switch 的 case 里怎么写 else」（2026-10-15 深夜）

**答案**：Go 的 `case` 没有 `else`，`else` 只属于 `if`。case 想表达"否则"有三招：① case 体内写 `if/else`（case 体就是普通代码块）；② 拆互补 case（`case !条件:` 就是 else 效果，语法合法）；③ `default:` 当 else 兜底。

**当场修掉的问题（`mian/领取成就.go`）**：用户写的 `case 主菜单列表: ... case !主菜单列表: ... default: ...` 里，`case !主菜单列表:` 会把"主菜单列表为假"全兜住 → **`default` 永远轮不到，成死代码**。互补 case 和 default 只能留一个（已删 `case !主菜单列表:`，保留 default，照 `灵力修炼.go` 样板）。另：`case 主菜单列表:` 里注释写"点【主菜单】【成就】"但漏了 `查找点击延时("主菜单")`，已补。

**教训**：`switch { case 条件A: case !条件B: default: }` 这种"否定 case + default"并存是经典死代码陷阱——`case !X` 恒覆盖 X 为假的一切情况。要兜底就只用 `default`，或者只用互补 case，别两个都写。
